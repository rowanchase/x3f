# 2026-02-26: Fundamental Color Matrix Analysis

## Summary

After deep analysis of the color processing pipeline, I've identified the **root cause** of our color inaccuracies. The issue is not just parameter tuning - it's fundamentally about how the color matrix is computed.

## Key Discovery: Root Cause

### The Color Matrix Problem

In `src/x3f_process.c` lines 253-284, there are **two approaches** to computing the raw→XYZ matrix:

**Approach A** (lines 257-264) - WRONG for Merrill:
```c
if (x3f_get_camf_matrix_for_wb(x3f, "WhiteBalanceColorCorrections", wb, 3, 3, cc_matrix)) {
    double srgb_to_xyz[9];
    x3f_sRGB_to_XYZ(srgb_to_xyz);
    x3f_3x3_3x3_mul(srgb_to_xyz, cc_matrix, bmt_to_xyz);
}
```

This assumes `WhiteBalanceColorCorrections` is a raw→sRGB matrix, but it's actually:
- A color CORRECTION matrix meant for sRGB→sRGB adjustments
- Contains values like: [[1.90, -1.76, 0.86], [-1.68, 3.53, -0.85], [1.08, -4.91, 4.83]]
- These are NOT the same as raw→XYZ conversion matrices

**Approach B** (lines 266-276) - CORRECT but NOT USED:
```c
else if (x3f_get_camf_matrix_for_wb(x3f, "WhiteBalanceIlluminants", wb, 3, 3, cam_to_xyz) &&
         x3f_get_camf_matrix_for_wb(x3f, "WhiteBalanceCorrections", wb, 3, 3, wb_correction)) {
    // Properly computes raw→XYZ from illuminant + correction matrices
}
```

### The Real Problem

Merrill X3F files:
- **DO** contain `WhiteBalanceColorCorrections` (e.g., AutoCCMatrix, SunlightCCMatrix)
- **DO NOT** contain `WhiteBalanceIlluminants`

Since Approach A succeeds, Approach B is never tried. The result is an **incorrect color matrix** that produces:
- Green cast (requiring our 0.895 correction)
- Excessive saturation (requiring 0.62 desaturation)
- Massive a-channel errors (DeltaE ~50+)

## Research Findings

### 1. dcraw Approach (from code search)

dcraw's Foveon processing (`foveon_interpolate()`):
1. Loads CAMF metadata
2. Gets `WhiteBalanceIlluminants` + `WhiteBalanceCorrections`
3. Computes: `rgb_cam × illuminant_matrix × wb_correction`
4. Applies diagonal WB multipliers

Key difference: **dcraw doesn't have hardcoded matrices for Merrill** - it relies on CAMF data.

### 2. Academic Research: Foveon Merrill Inherent Limitations

From Jim Kasson's blog (Dec 2023):
- Foveon Merrill has Sensitivity Metamerism Index (SMI) of **~82**
- High-quality cameras score 88-98+ (perfect = 100)
- This is fundamentally limited by the sensor physics

From JOSA 2015 paper (Mohammadzadeh Darrodi et al.):
- Measured actual Sigma SD1 Merrill spectral sensitivity
- Found that estimation techniques don't work well
- Best results require measured spectral data

### 3. Why Sigma Photo Pro Works Better

SPP uses:
1. Proprietary color matrix computation we can't replicate
2. Possibly custom spectral sensitivity data
3. Additional processing (unknown) for color refinement
4. Scene-adaptive corrections

## Paper Review Addition: Fent & Meldrum (2016) on Foveon Sensor

**Paper**: "A Foveon Sensor/Green-Pass Filter Technique for Direct Exposure of Traditional False Color Images"  
**Journal**: Journal of Imaging, 2016

### Key Technical Findings for X3F Merrill Processing:

1. **Foveon F20 Sensor** (used in Sigma SD1 Merrill, DP1/2/3 Merrill):
   - 3-layer stacked structure: Blue (top), Green (middle), Red-NIR (bottom)
   - Full spectrum: 400-1100nm (when IR filter removed)
   - Red-NIR layer records BOTH red visible (600-700nm) AND NIR (700-1100nm)

2. **Quantum Efficiency Data** (from Table 4):
   | Wavelength | Blue Layer | Green Layer | Red-NIR Layer |
   |------------|------------|-------------|---------------|
   | 420-490nm  | 2.8        | 1.9         | 0.4           |
   | 500-575nm  | 10.6       | 13.2        | 9.0           |
   | 600-675nm  | 1.1        | 1.9         | 2.8           |
   | 600-1050nm | 4.0        | 7.3         | 14.6          |

3. **Optimal White Balance**: 4100K preset (not 5500K daylight)
   - Equivalent to 85C filter on daylight
   - Emphasizes red-NIR layer by factor of ~3 over blue
   - Sigma Photo Pro likely optimized for this setting

4. **Spectral Sensitivity Source**: Data from Alternate Vision Corp
   - F13 sensor curves modified for F20 version
   - Cross-reference available for different Foveon versions

5. **Color Processing Model**:
   - Multiply sensor QE by filter transmission
   - Apply color temperature correction
   - Sum area under curves for RGB ratios
   - This matches our pipeline: Raw → QE → Matrix → WB → Output

6. **Merrill Sensor Sensitivity**:
   - Extremely sensitive to green balance
   - Too much green = cyanish image
   - Too little green = NIR overwhelms (red/magenta)
   - Spatial gain compensation critical (enabled by default for Merrill)

### Implications for Our Project:
- Color matrices in x3f_matrix.c should be verified against this QE data
- White balance handling may need 4100K optimization
- Cross-layer spectral overlap needs proper handling
- Spatial gain values may need recalibration

## Implementation Work: Processing Pipeline Improvements

### Analysis of Empirical Corrections

Reviewed the empirical corrections in `src/x3f_process.c`:
1. SPP exposure compensation: 2.5x (confirms SPP applies additional brightness)
2. Green cast correction: green 0.895x, blue 1.19x, red 1.17x
3. Global desaturation: 0.62x (38% desaturation)
4. Shadow and highlight desaturation

### Applied Improvement Based on Paper

Adjusted blue channel correction multiplier from **1.19 to 1.06** based on Fent & Meldrum QE data:

**Rationale:**
- Paper shows Foveon F20 QE at 500-575nm: Blue=10.6, Green=13.2
- Blue layer has ~20% lower QE than green
- Original 19% boost (1.19) was too aggressive
- Adjusted 6% boost (1.06) better matches sensor physics

**Results on _P2M0927.X3F:**
- RMSE: 11.94 → 11.48 (3.9% improvement)
- MAE: 8.99 → 8.70 (3.2% improvement)  
- B-channel MAE: 12.40 → 11.48 (7.4% improvement)
- B-channel mean error: 4.23 → -0.38 (nearly zero bias)

### Testing on Multiple Files

Results across reference files:

- _P2M0928.X3F: RMSE = 14.68 (variation due to scene content)
